# Known gaps — the deliberate debts, in full

> The inventory of debts this project carries **on purpose**, each with the
> reasoning that made it a decision rather than an oversight, the palliative
> that stands in for the fix, and the gate that would reopen it. AGENTS.md
> lists these one line each; this file is the depth. A gap that gets closed
> moves its lesson to the place that outlives it (a DECISIONS.md anchor, a test,
> a comment at the site) and leaves this file.

## The composition root (`AppCore.init`) is mostly unpinned, by decision

Audit of the `App` layer: **224 wiring points, 181 with no test at all**, a single root cause already confessed in a comment in the suite itself — *no test constructs an `AppCore`*, because the `init` touches ~8 system edges outside the `SystemGraph` (the AX permission and its poll, the event tap, `SMAppService`, the lock source, workspace observers, real `NSPanel`s, `UserDefaults`).

Pinned: **26 static seams** the `init` calls, each called from a test without constructing an `AppCore`. Ten are `wire*` joins where a mistake **compiles, runs and produces a plausibly wrong app** — the brightness echo routed by authority, the post-apply poke, the escalation mirror the menu reads, the handback stand-down, the active source's end, Low Power Mode, the three preventive-reinstall triggers (wake, screen parameters, unlock), and the neighbour's indicator handoff (`AppCoreNeighbourOSDWiringTests`); `makeNeighbourSource` builds the neighbour's source with its local sibling; the rest are decisions the `init` delegates (login item, style declaration and overrides, HUD placement and its preview, the screen roster, the welcome tour, the Accessibility request, the chain and key-target notices). The tests live in `CremaTests/App/` (`AppCoreWiringSeamTests`, `AppCoreHandbackWiringTests`, `SuppressionUnlockReinstallSeamTests` among them), and `MediaKeyChainReconcilerTests` calls the chain notice.

The rest **stays**, in five classes:

1. Constructor arguments the type already decides, where the only conformer is the production one and a test would assert a distinction no observer makes.
2. Edges whose only honest observer is the real system (`SMAppService`, a live cursor, `describeAll()`, Settings URLs, Info.plist keys) — there a test is either tautology or a trip to hardware, and a mistake shows up on first launch.
3. `start()` and the retention guard, which break **loudly** on the build's first run, not silently.
4. What sits behind `#if DEBUG`, the demo graph. The production graph is wired once, in `makeProductionGraph`, which the Debug-real and the Release branch both call, so the branch the Debug-hosted suite never compiles carries no wiring of its own.
5. The idea of an `AppCore` over doubles, which **moves** the hole instead of closing it — and an end-to-end test of the graph is less mutation-sensitive per line than the `wire*` seams, which fails the house criterion outright.

Two named survivors, accepted: `MenuStatus.Action` (a 5-case switch — a button could re-register the login item under the re-enable-suppression label; the fix asks for a new protocol, more structure than the risk pays for) and `AppCoreAutomation:14` (a boolean inversion that would erase the Permissions line and leave a blocking consent poll running forever). A residue every `wire*` shares, and one still worth stating: they pin the **wiring**, not the `init` line that installs it.

What generalises: a rule whose call site no test reaches survives its own mutation, and a seam extracted for it only moves the untested line by one — this entry's verdict covers those cases too.

## Three clamps into `0...1` are spelled apart, and the gate on sharing them is met

`BrightnessConversion` and `VolumeConversion` spell `normalize`/`denormalize` as the same eight lines: NaN reads as 0, everything else clamps into `0...1`. A shared helper stays unwritten because volume and screen brightness are independent domains, and folding them would couple Core Audio's edge to DisplayServices' for four lines each. This is NOT the `shared-skin-skeleton` case, whose ~120 lines carry the record of a fix that reached two skins and missed the third.

The gate this entry set — a third domain wanting the clamp, or a divergence — is met by `BetterDisplayCommandTranslation.setBrightnessRequest`: it clamps into `0...1` too, saturates the infinities the same way, and refuses NaN (nil, read as a failed apply) where the two conversions return 0, because a fabricated 0 would darken a display nobody asked to darken. A helper for all three therefore needs a NaN policy per caller. Whether to write it, or keep three spellings that each document their contract in full, is the maintainer's call; until then the palliative is that documentation, so a reader fixing one site can see what the others promise.

## The perpetual animations carry no time veto

Two animations loop for as long as their surface shows: `WaveformGlyph` (the desktop skins) dances under `dances(animating:reduceMotion:lowPower:)`, and a title too long for the expanded player scrolls under `MarqueeMotion.moves` (docs/DECISIONS.md: a-long-title-scrolls-where-it-is-read). Both answer the two app-wide vetoes and nothing else; no surface the app carries has a time veto (docs/DECISIONS.md: the-lock-screen-was-built-and-taken-out records the one the lock surface had). The marquee runs only while the expanded player is up, which tucks on a timer except under the pointer; its `TimelineView` draws every frame, the rests included.

The case for adding one is NOT established and should not be built on the "runs all night" framing alone: the display sleeping does not stop compositing (measured with a probe that is not in the tree: the process went on compositing for 67 s in the dark, and only SYSTEM sleep stopped it), but four 12 pt bars are a different order of cost from a full-screen blurred bitmap transform, and nobody has measured which side of "worth a timer" they fall on. What would settle it: a power reading with a surface lit and playing, against the same surface paused, on a Mac configured not to sleep. Until then the honest position is that the veto is missing on purpose rather than by oversight.

## A process finishing is not its children finishing

Two orphaned `python` processes from a documentation review were found at ~100% CPU each, one hour and ten minutes after the run completed, adopted by launchd when the agents that spawned them died. They came from a `/System` scan the prompt itself invited by offering it as an alternative to the prepared corpus. Two palliatives: a prompt that hands agents a prepared file must not ALSO offer the expensive path, and closing a round includes `ps` for stray children, not just the run's own completion.

**The same class lives in SHIPPED TOOLING:** `release.sh`'s launch smoke starts the app, kills its PID after 5 s and `rm -rf`s the temp bundle, but Crema spawns the mediaremote-adapter as a long-lived perl child that does NOT die with its parent (measured on the release machine: an adapter from a smoke run three minutes earlier was still alive and streaming, against a bundle path already deleted, and would have survived until reboot), so two `pkill -f` calls matched on the mktemp path reap it on both the pass and the fail branch — matched on the path precisely so it cannot touch the adapter of the author's real installed copy, which is the app they are using to test.

The lesson generalises past this script: **killing a process is not killing what it started, and a `rm -rf` afterwards makes the orphan invisible rather than absent.** The app-hosted test target leaks the same child for the same reason; that one is short-lived per run but shows up in `ps` after a long session. `release.sh`'s test gate, when it has to kill an `xcodebuild` hung after its verdict, also reaps the test host and its adapter by this project's Debug products path.

## The keyboard-backlight client is resolved once, and no edge re-creates it

`CoreBrightnessKeyboardBridge.init` resolves the private `KeyboardBrightnessClient` — the class, its selectors and one instance — and holds that instance for the life of the process. Everything downstream of it is deliberately per-operation, because a frozen handle is exactly how this family dies: the keyboard ID is re-enumerated on every read, write and availability check (`copyKeyboardBacklightIDs` + `isKeyboardBuiltIn:`), which closes the latent sibling of the display bridge's stale-ID death (docs/DECISIONS.md: J2-display-id-stale). The client is the one handle still frozen, and the IDs are enumerated OVER its connection: if that connection dies, every read returns nil, every write returns false, `isAvailable` asks the dead client and answers no, and the channel reports itself absent for the rest of the session. The four preventive-reinstall edges rebuild the media-key tap, not this.

Why it stays: the fix is not the code, it is knowing what to write. Re-resolving on a wake edge is a handful of lines, but whether a dead client is even reachable — whether the connection dies at all, whether the symptom is a nil read or a hang, whether a fresh client on the same machine recovers — is a hardware question nobody has answered here. The one probe that touches this class (`scripts/probes/hardware-probes.swift`, probe 2) hammers it from three threads to settle whether the bridge must serialize; it says nothing about a client that has died. Writing a recovery path against a failure nobody has reproduced would ship a rebuild on every wake for a fault that may not exist, on the border where every call is a private-framework round trip — and it would be untestable in the only way that counts, since the failure it recovers from cannot be staged.

The palliative is that the degradation is honest and total rather than partial: no crash, no fabricated value, no half-live channel — `isAvailable` answers false, the HUD stops surfacing, the keys go back to the system with their native feedback, and a relaunch restores everything. The other half of the channel already self-heals in the same shape a recovery would need: `PolledBrightnessSource.startPollingIfAvailable` re-arms the cadence at the first key after the channel answers again, so a bridge that DID come back would need nothing else added around it.

Reopening gate: a reproduction on hardware — a session where the backlight HUD stops while the keys still work, with a probe showing the enumeration empty (or the read failing) against a freshly constructed client that answers. That reproduction is also the test: the bridge's class resolver and ID provider are already injectable, so a re-resolve can be pinned without touching CoreBrightness.

## SwiftLint's analyzer rules are off, so nothing in CI looks for dead code

`.swiftlint.yml` declares no `analyzer_rules`; `unused_declaration` and `unused_import` need a compiler log (`swiftlint analyze --compiler-log-path`), which means CI would build twice and gain a step that can break on its own. Measured by hand instead: zero unused `private` declarations across the whole tree, and the four internal types with no cross-file reference each have a use in their own file. The gap is that this is a one-off sweep, not a gate — a declaration that dies tomorrow dies unnoticed, and so does one born dead in a file added since. The palliative is that sweep, and the decision to spend CI minutes on it is the maintainer's.

## The style declaration's adoption runs at every launch, with no exit

`Preferences.adoptDeclaredStyleFromOverrides` carries a pre-declaration install's style into the global declaration: before v1.4.0 the picker wrote per-display keys only, so that is where the user's choice lives. It runs on every launch, before the first panel roster, and nothing says when it may stop. It stays because Sparkle lets any older install update straight to the newest build, so an upgrade from before v1.4.0 can arrive at any time. The palliative is that it is idempotent and cheap: the presence of the declaration key closes it for good, an install with no override writes nothing, and what is left on every other launch is one key read. Reopening gate: a decision to stop supporting updates from installs older than v1.4.0; then the call and the method go, with the overrides untouched.

## The Privacy panes are opened by a hand-built URL

The Accessibility and Automation panes are opened with `x-apple.systempreferences:com.apple.preference.security?Privacy_…` (`AppCore.requestAccessibilityAccess`, `AppCore.openAutomationSettings`), the undocumented identifier kind Apple has already renamed once, and `NSWorkspace.open`'s `Bool` is discarded, so a renamed pane is a button that does nothing and says nothing. It stays because there is no public opener: the macOS 27.0 SDK's only `openSystemSettings…` method is `SMAppService.openSystemSettingsLoginItems`, which the Login Items repair already uses. The palliative covers Accessibility alone: the request raises the system's own prompt, which registers the app in that list; for Automation a dead link has no fallback. Reopening gate: Apple shipping an opener for the Privacy panes, or a renamed pane reported from the field. The cheapest first step then is logging the `false` that `open` returns.

## A guard in the native-OSD suppressor survives its own mutation

`MediaKeyInterceptionOSDSuppressor.noteAbsent` re-checks the engagement generation after its `await`, so a stale apply cannot write an absent capability into a newer engagement. The guard is not pinned, and removing it survives the suite: the window needs a stale apply to resume after an engage flip, and nothing observable marks that moment (the absent set has no test-visible snapshot, and a `.noOp` fires no callback), so every probe either presses too early, where both behaviours agree, or retries until the re-check has healed the difference. A test that only pretends to pin it is not kept. The palliative is the comment at the site, which states the gap and its price. Reopening gate: a second reason to give the decider an absent-set snapshot, the way it already exposes `suspendedDomains`; with that snapshot the test can be written honestly.

## The browser filter runs after translation and knows browsers by prefix

`MediaSourceFilter` drops browser media in the Coordinator, after the adapter's line has been buffered, decoded and translated, and it recognises a browser by a fixed list of bundle-ID prefixes. A website's title, position and artwork therefore reach the line buffer and the translation even with browser media off, and in a browser missing from the list (or a Safari web app, let through on purpose) they reach the artwork decoder and the views too. It stays because the filter is a noise policy, not a security boundary. What keeps that path safe is the bounds at the border, which do not depend on it: the position bounded by `NowPlaying.bounded`, the line buffer's ceiling, and the artwork gate in `ArtworkDecoding`. Reopening gate: a sink that relies on the filter to keep website data out.

## A signed feed can be served again later

The appcast's signature proves who wrote a feed, not when: the feed signed for 1.5.0 is still validly signed today. Whoever can publish `docs/appcast.xml` (a merge to `main`, GitHub Pages) can serve an older signed feed and freeze clients at that version, telling them nothing newer exists. It cannot cause a downgrade: Sparkle 2.9.4 offers only a newer version, and its installer rejects an older one. It stays because Sparkle checks no freshness on a feed, and the only publishers are the maintainer and GitHub. The palliative is the protection on `main` (docs/GITHUB.md), and a frozen client still runs a signed build. Reopening gate: Sparkle gaining a freshness check, or a second party gaining write access to `main`.

## BetterDisplay's channel carries no sender identity

Anyone in the session can post `pro.betterdisplay.BetterDisplay.osd`, or answer a request on `.response`, and `NSDistributedNotificationCenter.h` offers no way to know who posted while telling the receiver to treat the data as untrusted. A forged reading draws a bar of the poster's choosing, keeps the HUD up and sets the level a failed drag rolls back to; a forged answer reads as BetterDisplay's verdict, and a forged no sends the drag to the system actuator. A forged answer to a handoff read can also record the wrong original, which the hand-back then writes into BetterDisplay's own switch. It stays because the protocol is the neighbour's and has no authentication. The palliatives: no payload writes anything by itself — a brightness write starts with the user's drag, and the handoff, on the user's opt-in, writes only BetterDisplay's two feedback switches, each between its two values; a payload naming no display or an impossible one is dropped; the local source stands down only for a report about its own panel; and the integration claim needs BetterDisplay running. Reopening gate: BetterDisplay offering an authenticated channel, or a forged payload found reaching a write without a drag or the opt-in.

## The vendored adapter's binaries carry no recorded origin

`ThirdParty/mediaremote-adapter` ships a framework and a test client built on the maintainer's machine from upstream tag v0.7.6 (its README), and no upstream commit SHA or digest of those binaries is recorded anywhere. What ships therefore cannot be checked against upstream or rebuilt to the same bytes. It stays because no adapter update has called for a rebuild since. The palliative: release.sh signs both binaries with Crema's identity, so a swap after release breaks the seal, and the Perl script beside them is plain text in the repository. Reopening gate: the next adapter update, which records the commit SHA and each binary's sha256 in its README.

## Files inside Crema.app can be replaced by whoever can write it

The adapter's Perl script and framework are resolved from the bundle at run time and started as Crema's children. With library validation off on the self-signed app (docs/DECISIONS.md: self-signed-runtime-without-library-validation), the app itself also loads a library of any signer from its own bundle. A process that can write `Crema.app`, which is user-owned after a drag install, therefore runs code as Crema or as its child while the main executable stays intact. It stays because closing it needs facts nobody has measured here: whether macOS's App Management protection covers a self-signed app, and whether TCC checks the bundle's resource seal before honouring the grant. A signature check at spawn would still leave the window between check and exec. The palliatives: the code seal covers the bundle, so a swap shows in `codesign --verify`, and the DYLD-environment route into the app's own executable, which needs no write at all, is closed by its hardened runtime.

The same route stays open one level down. On the self-signed path `release.sh` re-signs every nested binary (Sparkle's framework and its helpers `Autoupdate`, `Updater.app` and the two XPC services; the adapter's framework and test client) with Crema's identity but without the runtime, so a process of the same user can start one of the executables among them with `DYLD_INSERT_LIBRARIES` and run code inside it. It is marginal next to the bundle swap above: none of them holds the Accessibility grant, and whoever can write the bundle already has the larger door. It stays because the runtime on those helpers is unmeasured with a self-signed identity, and the launch smoke exercises only the app. Reopening gate: a measured update cycle with the helpers signed with the runtime (and validation off where they load Sparkle), or a Developer ID, which signs them all with it.

Reopening gate for the whole entry: a primary source on App Management and TCC for a self-signed bundle, or a Developer ID, which turns library validation back on.

## Multi-display hover and two motion constants rest on unmeasured ground

Two hover hypotheses live only in comments at their sites, each deliberately unimplemented until hardware answers it. `Coordinator.pointerSurfaces` is one global record keyed by layer kind (`PresentationLayers.Surface`), written by every panel's monitor, so with two displays each drawing a `.hud` panel the last writer could in principle mask the other display's state. `SurfaceHoverMonitor` notes that macOS may throttle `mouseMoved` delivery to the global monitor while a panel is interactive and the app an inactive accessory. Neither has a probe, and a speculative fix (a per-display record, a re-sampling timer) would ship behaviour nobody has seen fail.

Two constants were measured without a probe kept in the tree: `SurfaceAnimation.closeResponse` (0.35, from a release-latency budget, its date, commit and invalidating signal at the site) and `CapsuleTrack.knobSize` (17.5×14 pt, read off the Tahoe banner on macOS 26.5.2). Re-deriving either means measuring from scratch.

Reopening gate: a two-panel hardware probe with counters for the hover paths (pointer records per display, `mouseMoved` delivery while interactive), or a probe that re-measures either constant; the probe then lives in `scripts/probes/` beside the site it settles.
